# Архитектура и выбор стека

## Правила выбора

Сначала ограничения и пользовательские сценарии, потом технологии. Предпочитай экосистему с актуальной документацией, активной поддержкой, простым запуском и понятными тестами. Перед утверждением стека проверь точные текущие версии и условия хостинга.

## Базовые стартовые варианты (не универсальный рейтинг)

| Задача | Разумный стартовый вариант | Когда выбрать другое |
|---|---|---|
| Интерактивный сайт / web app | TypeScript + React / Next.js или Vite в зависимости от SEO и серверной логики | Статический сайт может обойтись без сложного framework |
| Backend/API | TypeScript + Fastify/NestJS или Python + FastAPI | Выбирай язык/фреймворк команды и окружения; не переписывай ради моды |
| Скрипты и интеграции | Python или TypeScript, cron/webhook/очередь по необходимости | Не разворачивай инфраструктуру очередей для редкой одноступенчатой задачи |
| Telegram-бот | Python (aiogram) или TypeScript (grammY/Telegraf); webhook для production при подходящем хостинге | Проверить актуальные версии библиотек и требования Telegram перед сборкой |
| Простое CRUD-приложение | PostgreSQL + ORM с миграциями; при необходимости managed backend | SQLite хорош для локального/однопользовательского варианта; не выбирать managed service без анализа условий |
| Desktop | Tauri/Electron или нативные средства ОС | Учитывай подпись приложения, обновления, права и размер дистрибутива |
| Мобильное приложение | Нативный стек или React Native/Flutter | Решение зависит от функций ОС, офлайн-режима, платформ и навыков |
| Автоматизация бизнес-процесса | Сначала ручная карта процесса, затем API/webhook; n8n/аналог, если помогает | Для критического процесса важны версия, бэкапы, наблюдаемость и переносимость |

Эти сочетания — стартовые эвристики, а не обещание, что конкретный стек лучший или бесплатный. Перед реализацией верифицируй актуальные версии, лицензии, совместимость и цену.

## Минимальные архитектурные правила

- Разделяй UI, доменную логику, хранение и интеграции настолько, насколько это реально улучшает тестирование и заменяемость.
- Для небольшого продукта по умолчанию начинай с модульного монолита; распределённую архитектуру вводи только по измеримой причине.
- Для БД используй миграции, ограничения целостности, индексы под реальные запросы и стратегию резервного копирования.
- Внешние вызовы имеют тайм-аут, ограничение повторов, обработку ошибок и защиту от двойного выполнения там, где это важно.
- Для webhook проверяй подпись/секрет платформы, повторные доставки и идемпотентность.
- Для файлов ограничивай размер и тип, проверяй содержимое, храни отдельно от исполняемого кода и не доверяй имени/расширению.
- Для долгих задач используй фоновые очереди только когда нужны надёжные повторы, расписание или пользовательский запрос должен быстро ответить.
- Все URL, API-ключи, почта, домен, ID бота и параметры окружения выноси в конфигурацию.

## Минимальный комплект нового репозитория

- `README.md` — установка, настройка, запуск, тесты, troubleshooting.
- `.env.example` — только имена переменных и демонстрационные не-секретные значения.
- `.gitignore` — env, build, cache, secrets, временные файлы.
- `AGENTS.md` — контекст для coding agents.
- тесты для основной логики и критических сценариев.
- миграции / seed для БД при наличии.
- CI-проверки, если репозиторий и хостинг это поддерживают.
- логирование без секретов и персональных данных.

## Не делать по умолчанию

Не добавлять Redis, Kafka, Kubernetes, отдельный сервис авторизации, векторную БД, сложный state manager, платную аналитику, отдельный AI-агент и большой UI kit, пока нет доказанной потребности. У каждого нового компонента должны быть обоснование, цена, способ обновления и сценарий отказа.
