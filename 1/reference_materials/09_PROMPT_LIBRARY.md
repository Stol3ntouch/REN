# Библиотека промптов Dev Factory

Подставляй ID проекта, прикрепляй актуальные файлы и уточняй среду. Не проси «сделать всё идеально» без критериев приёмки.

## A. Идея → план/ТЗ

> [ID: WEB-001] Прочитай `03_PROJECT_BRIEF_TEMPLATE.md`. Преобразуй мою идею в короткое ТЗ: пользователи, проблема, сценарии, MVP, критерии приёмки, модель данных, риски и план тестирования. Задай только блокирующие вопросы; остальные допущения перечисли. Пока не пиши код.

## B. Аудит существующего репозитория

> [ID: APP-001] Сначала изучи структуру и существующие инструкции репозитория. Ничего не меняй. Опиши архитектуру, команды сборки/тестирования, текущие незавершённые области и топ-10 рисков/дефектов с путями к файлам. Отдели подтверждённое от предположений. Укажи, какие дополнительные файлы нужно прочитать для надёжного вывода.

## C. Архитектура

> [ID: BOT-001] На основе согласованного ТЗ предложи минимально достаточную архитектуру. Сравни не больше 3 стеков по простоте, цене, надёжности, поддержке, деплою и vendor lock-in. Проверь текущую официальную документацию и версии. Покажи потоки данных, роли, схему БД, обработку ошибок и план отката. Не реализуй до выбора.

## D. Реализация вертикального среза

> [ID: APP-001] Реализуй только следующий срез: [описание]. Сначала уточни существующее поведение и добавь/обнови тест, воспроизводящий требуемую логику. Затем внеси минимальные изменения, запусти целевые тесты, связанные проверки, lint/typecheck/build, если доступно. Не меняй несвязанные части. В конце перечисли файлы и результаты реальных команд; не заявляй, что непроведённые проверки прошли.

## E. Починка бага

> [ID: APP-001] Воспроизведи баг [шаги/лог]. Определи предполагаемую первопричину, добавь регрессионный тест, проверь его падение, исправь причину, выполни тесты и проверь соседние сценарии. Сохрани поведение вне бага. Если не можешь запустить код — явно скажи и дай точные команды.

## F. Независимый code review

> Проведи независимый review изменений как критичный senior reviewer. Сначала ищи критичные дефекты и security issues, затем логику, регрессии, performance и поддержку. Не переписывай код. Для каждого finding: severity, файл/строка, воспроизводимый сценарий, последствия, минимальное исправление. Если серьёзных находок нет — перечисли проверенные области и ограничения review, не придумывай замечания.

## G. QA-тест-план

> По ТЗ создай матрицу тестов: ID, предусловия, шаги, ожидаемый результат, тип, приоритет, автоматизация. Обязательно включи отрицательные сценарии, права доступа, тайм-ауты, повторы, пустые и граничные данные. Не повторяй сценарии без новой ценности. Отметь, какие тесты можно запустить автоматически сейчас.

## H. Безопасность

> Проведи threat modeling для [ID]. Опиши assets, trust boundaries, entry points, злоупотребления, вероятность/ущерб и меры. Особое внимание: authz, secrets, injection, XSS/CSRF/SSRF, uploads, webhooks, prompt injection, data leakage, rate limits, dependencies, logs. Отдели фактические уязвимости от гипотетических. Ничего опасного в production не меняй без одобрения.

## I. UI/UX-аудит

> Проверь пользовательские сценарии, иерархию интерфейса, мобильную адаптацию, клавиатуру/фокус, контраст, сообщения об ошибках, empty/loading/success states. Для каждого замечания — приоритет, экран/компонент, влияние на пользователя и минимальное улучшение. Не предлагай только субъективные изменения без объяснения.

## J. Локальный запуск / Docker

> Подготовь воспроизводимый запуск этой кодовой базы на [Windows 11 / macOS / Linux]. Сначала проверь актуальные версии и фактические команды проекта. Если Docker уместен, создай compose/config, health check, volumes, `.env.example` и инструкции обновления/бэкапа. Не публикуй секреты, не используй `latest` без обоснования, не обещай успешный запуск без проверки.

## K. Деплой

> Сравни 2–3 текущих варианта хостинга для [нагрузка/регион/бюджет]. Проверь официальные тарифы, ограничения и сохранность данных на дату ответа. Подготовь checklist деплоя, переменные окружения, миграции, TLS, домен, логи, бэкап и rollback. Не создавай платные ресурсы и не публикуй приложение без моего подтверждения.

## L. «Почти готово» → выпуск

> Выполни Definition of Done из `05_DEFINITION_OF_DONE.md`: сверь требования с реализацией, составь список проверок и выполни доступные. Проведи ревью файлов, документации, ошибок, безопасности и запуска с чистой среды. Итоговый статус должен быть готово / условно готово / не готово. Не скрывай проваленные или непроведённые проверки.

## M. Оптимизация без переписывания

> Найди измеримый bottleneck или дорогой/ненадёжный участок. Сначала предложи метрику и план замера, затем минимальную оптимизацию и регрессионные тесты. Не оптимизируй без измерений и не меняй архитектуру только ради моды.

## N. Проверка спроса для продукта

> Сформулируй для идеи [описание] проверяемую гипотезу клиента, болезненную задачу, существующие альтернативы, сигнал спроса и дешёвый 7-дневный эксперимент без платной рекламы. Используй свежие источники, цитируй даты и отделяй факты рынка от предположений. Не начинай разработку полного продукта до подтверждения интереса.
