# C02 — RBAC в БД, пользователи и роли, журнал действий, уведомления (хранилище)

**Требования:** G46, G47
**Зависит от:** C01
**Зона:** `src/domain/admin/**` · `src/server/db/repositories/{staff,roles,audit,sessions,notifications}.ts` · `migrations/1100-1149` · `src/app/admin/(panel)/{staff,roles,audit}/**` · `src/app/admin/(auth)/**` · `scripts/admin-create.ts` · `tests/rbac/**` · `tests/admin/{staff,roles,audit}*.test.ts*`
**Волна:** 14
**Ревью:** да — права, пароли, сессии
**Модель:** сильная

## Что должно заработать

Права и роли живут в БД: сид из шести ролей (суперадминистратор, администратор, менеджер, контент-менеджер, сотрудник склада, специалист сервиса), создание собственных ролей и правка набора разрешений матрицей флажков. Сотрудники: создание, правка, назначение роли, блокировка и возврат доступа (с немедленным завершением сессий), смена пароля, безопасный сброс пароля. Журнал действий с фильтрами. Хранилище административных уведомлений (таблица и сервис `notify()`), которое используют остальные тикеты.

## Из брифа, дословно

> «Права должны задаваться по принципу RBAC и проверяться на backend»
> «Это исходный набор ролей, а не жёсткий список. Предусмотри создание собственных ролей и изменение разрешений»
> «Блокировку и восстановление доступа. Смену пароля. Безопасное восстановление пароля. Завершение сессий при блокировке»
> «Не создавай заранее известные пароли для администратора и не помещай секреты в исходный код»
> «Добавь фильтрацию по пользователю, периоду, типу действия и объекту»

## Критерии приёмки

- [ ] Таблицы `roles(id, code UNIQUE, name, is_system, created_at)` и `role_permissions(role_id, permission)`; `staff.role` заменён ссылкой `role_id` (миграция пересоздаёт `staff` без CHECK admin|manager с копированием данных: существующие `admin`→роль admin, `manager`→manager, первый admin остаётся рабочим; откат невозможен без бэкапа — миграция проверена тестом на копии данных)
- [ ] Список `Permission` расширен ровно ключами из `interfaces.md` (35 новых), старые 15 сохранены как действующие; сид ролей идемпотентен (повторный запуск не затирает правки админа в `role_permissions` системных ролей кроме `super_admin`); `super_admin` получает все права автоматически, не удаляется, не редактируется и последнего суперадмина нельзя заблокировать/понизить
- [ ] `requirePermission`, `withStaffPermission`, `requireStaffPage`, `hasPermission` работают от БД (кэш прав в сессии/процессе с инвалидацией при правке роли — изменение роли действует на уже открытые сессии не позднее следующего запроса); тест: изменил роль → доступ пропал без перелогина
- [ ] `/admin/roles` (право `roles.manage`): список ролей, создание, переименование, дублирование, удаление несистемной роли без сотрудников, матрица разрешений по группам с флажками; `/admin/staff` (`users.manage`): создание (пароль ≥10, не печатается и не логируется, либо ссылка-приглашение на установку пароля одноразовая), правка имени/роли, блокировка и возврат (блокировка завершает все сессии сотрудника), сброс пароля (одноразовая ссылка через MailPort/outbox, TTL, токен в БД хешем) и смена пароля; нельзя понизить/заблокировать себя последним суперадмином; аудит каждого действия
- [ ] Безопасность: защита от повышения привилегий (сотрудник не может назначить роль с правами, которых нет у него, если не `roles.manage`; manager не видит/не правит чужие роли), блокировка перебора и Origin на каждом action, ответы не раскрывают существование логина при сбросе, тесты на каждый защищённый ops (admin/без права/без сессии)
- [ ] `/admin/audit` (`audit.read`): фильтры по пользователю, периоду (с-по), типу действия, объекту (entity+id), результату; серверная пагинация; запись содержит пользователя, действие, объект, id, время, результат (`ok|denied|error`), IP/user-agent хеш (без ПДн в открытом виде), безопасный контекст до/после через `maskPii`; события вход/выход/блокировки/изменение ролей/настроек пишутся; записи неизменяемы; экспорт CSV отфильтрованного (`audit.read`)
- [ ] Уведомления (хранилище): таблица `admin_notifications(id, type, title, body, entity, entity_id, href, severity, created_at)` и `admin_notification_reads(notification_id, staff_id, read_at)`; сервис `notify({type,title,body,href,entity,entityId,severity,audience:'permission:orders.read'|'all'})` (дедупликация по `type+entity+entityId` в окне), `listForStaff(staffId, {unreadOnly, limit})`, `markRead`, `markAllRead`, `unreadCount`; доступ только к уведомлениям, к которым у сотрудника есть право по `audience`; тесты (права, дедупликация, прочтение у каждого сотрудника своё)
- [ ] `npm run admin:create` создаёт суперадмина (пароль из ввода/ADMIN_PASSWORD, не печатается); существующие тесты rbac/admin зелёные (обновить, не ослабляя); `npm run check` и `npm run build` (NEXT_DIST_DIR=.next-c02) зелёные
