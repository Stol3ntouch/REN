## Что должно заработать

`PaymentPort` с тестовым провайдером: после оформления с «онлайн (ТЕСТ)» покупатель попадает на страницу «ТЕСТОВАЯ ОПЛАТА» с кнопками «успех» и «отказ»; результат приходит webhook'ом, подписанным HMAC (`PAYMENT_WEBHOOK_SECRET`). Заказ становится «оплачен» только по проверенному webhook. Проверяются подпись, id заказа, сумма и валюта; повтор события не меняет заказ второй раз. Возврат — через `refund`. В production тестовый провайдер выключен, без выбранного провайдера онлайн-оплата не предлагается. `DeliveryPort` с ручной реализацией «по согласованию с менеджером». Админка показывает статус портов («заглушка, не подключено»).

## Из брифа, дословно

> «До получения документации — интерфейс адаптера и тестовый режим, не фиктивная production-оплата»
> «Показывать только настроенные способы»
> «Повторное нажатие/повторный webhook не должны создавать дубли заказов или платежей»

## Критерии приёмки

- [ ] Webhook с неверной подписью, с суммой или валютой не как в заказе, с неизвестным заказом → отклонён, заказ не изменён (тесты)
- [ ] Один и тот же `event id` дважды → заказ переходит в «оплачен» один раз, платёж один (тест)
- [ ] Возврат браузера на `returnUrl` без webhook не ставит «оплачен» (тест)
- [ ] Сценарии: успех, отказ → `payment_failed`, таймаут провайдера (заказ не теряется, виден оператору), возврат → `refunded`
- [ ] Данные карты нигде не запрашиваются и не хранятся; секрет не попадает в логи и ответы
- [ ] При `APP_ENV=production` без настроенного провайдера метод «онлайн» недоступен; тестовый провайдер недоступен
- [ ] Метод доставки «по согласованию» не показывает выдуманной стоимости; статус портов виден в админке как «не подключено — заглушка»
