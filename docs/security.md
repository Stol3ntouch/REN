# Безопасность: что сделано и что нет

Проверено автотестами (`npm run check`) и сквозной проверкой живого сервера (`docs/qa-report.md`). Независимого аудита безопасности и тестирования на проникновение **не было**.

## Сделано

**Доступ и права**
- Права проверяются на сервере внутри каждого обработчика и server action (`requirePermission`); интерфейс не считается защитой. Менеджер прямым запросом к операции администратора получает 403 (тест).
- Роли: `admin` (всё) и `manager` (заказы, заявки, модерация, просмотр каталога/покупателей/журнала интеграций). Матрица — `spec.md` и `src/domain/admin/permissions.ts`.
- Чужой заказ, адрес, документ по идентификатору → 404, а не 403 (не раскрываем существование).
- Каждое изменение цены/статуса/роли/модерации/настройки/импорта пишется в журнал аудита; таблица журнала защищена триггерами от UPDATE/DELETE.

**Вход и сессии**
- Пароли — `scrypt` с солью; в БД только хеш. В cookie — случайный токен, в БД — его хеш. Cookie покупателя `rts_session` (HttpOnly, SameSite=Lax, Secure в production, 30 дней), сотрудника `rts_admin_session` (HttpOnly, SameSite=Strict, 12 часов) — разные таблицы и cookie.
- Блокировка при подборе пароля, лимиты на вход и сброс пароля (по IP и по email). Сброс пароля — одноразовая ссылка с ограниченным сроком.
- Гостевая ссылка на заказ — HMAC от `SESSION_SECRET`; в БД не хранится; смена секрета обнуляет ссылки.

**Запросы и формы**
- Проверка `Origin` у всех небезопасных методов (защита от CSRF), в том числе у форм заявок и корзины. Webhook платежей без Origin: доверие только подписи.
- Валидация `zod` на границах; SQL только параметризованный и только в репозиториях.
- Публичные формы: honeypot-поле, лимит по IP, чекбокс согласия с записью в `consents`.
- Сервер сам пересчитывает цены, суммы, наличие и промокод; значения из запроса игнорируются (тест и сквозная проверка с подменой цены).
- Двойная отправка заказа: уникальный ключ идемпотентности. Повтор webhook: уникальный идентификатор события.

**Заголовки и браузер**
- CSP с nonce на каждый запрос (`script-src 'self' 'nonce-…' 'strict-dynamic'`), `frame-ancestors 'none'`, `object-src 'none'`, `form-action 'self'`; источники изображений перечислены в `src/domain/seo/headers.ts`. HSTS на HTTPS в production, `X-Content-Type-Options`, `X-Frame-Options: DENY`, `Referrer-Policy`, `Permissions-Policy`. Нет `X-Powered-By`.
- Страницы кабинета, корзины, оформления, админки, поиска и API закрыты от индексации (`X-Robots-Tag` и `robots.txt`).

**Файлы и сеть**
- Скачивание изображений при импорте: только хосты из `IMAGE_HOST_ALLOWLIST`, блок частных/loopback/link-local адресов после DNS-резолва (защита от SSRF), лимит 5 МБ и 10 с, редиректы только на разрешённые хосты, проверка сигнатуры файла, перекодирование (EXIF удаляется), случайные имена.
- Импорт YML ограничен 20 МБ; описание товара санитизируется по белому списку тегов без атрибутов.

**Данные**
- Минимизация: собираются только поля форм. Email и телефон маскируются в логах, аудите и письмах менеджерам. Секреты читаются только из окружения, не логируются и не попадают в ответы; `.env.example` без значений (проверяет тест).
- Резервная копия не содержит `.env` и секретов (но содержит данные покупателей — см. `docs/backup-restore.md`).

**Платежи**
- Подпись webhook HMAC-SHA256, проверка суммы и валюты (RUB), защита от повторов; «оплачен» ставит только проверенный webhook. Оплата по отменённому заказу не меняет заказ и поднимает предупреждение (нужен возврат).
- **Тестовая оплата работает только вне production**: метод «онлайн (ТЕСТ)» в production принудительно выключен, страница `/pay/test/…` отвечает 404.

## Не сделано / ограничения

- Нет CAPTCHA и защиты от ботов сверх honeypot и лимитов по IP. Лимиты хранятся в SQLite одного процесса.
- Нет двухфакторной аутентификации сотрудников. Нет подтверждения email при регистрации покупателя.
- Нет шифрования БД и архивов «на диске» — это задача хостинга/оператора.
- Нет антивирусной проверки загрузок: изображения проверяются по сигнатуре и перекодируются, файлы других типов не принимаются, но сканера вредоносного содержимого нет.
- Не проведены нагрузочное тестирование, внешний аудит, сканирование уязвимостей production-конфигурации. `npm audit` показывает 5 замечаний уровня high в цепочке инструментов линтера (`braces` через `eslint-config-next`); в серверный код сайта они не попадают, но зависимости надо обновлять по мере выхода исправлений.
- Реальные платёжный провайдер, SMTP и 1С не подключались: подпись webhook проверена на тестовом провайдере, формат боевого провайдера может отличаться.
- Вне production, если `SESSION_SECRET` не задан, гостевые ссылки на заказ подписываются фиксированной dev-строкой. В production без секрета сервер не стартует; **не запускайте публично доступный сайт в режиме разработки**.
- Политика конфиденциальности и прочие юридические тексты — черновики, требуют проверки юристом.
- Консольные скрипты (`import:yml`, `admin:create`, `backup`, `restore`) рассчитаны на доверенного оператора на сервере.

## Если секрет утёк

1. Сменить значение (`SESSION_SECRET`, `PAYMENT_WEBHOOK_SECRET`, пароль SMTP, ключ провайдера) в окружении сервера и перезапустить приложение. Смена `SESSION_SECRET` обнуляет гостевые ссылки на заказы.
2. Для учётной записи сотрудника — деактивировать её в `/admin/staff` и завести новую (смены пароля сотрудника в интерфейсе нет; администратора можно добавить командой `npm run admin:create`).
3. Проверить журнал аудита (`/admin/audit`) за период.
