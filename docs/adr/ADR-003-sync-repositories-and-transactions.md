# ADR-003: Синхронные репозитории и транзакции как основа атомарности

## Контекст
План описывал репозитории и домен через `Promise`. Выбранный встроенный драйвер SQLite (ADR-001) синхронный. Заказы, оплата и импорт требуют атомарных операций «проверить и записать».

## Решение
Репозитории возвращают значения, а не промисы. Весь SQL лежит в слое репозиториев (исключение: чтение каталога, где SQL остался внутри доменного модуля каталога). Атомарность даёт одна функция транзакции с немедленной блокировкой записи; вложенные вызовы идут через точки сохранения. Тесты используют временную in-memory БД с применёнными миграциями.

## Почему
- Оборачивать синхронный драйвер в async отвергнуто: между проверкой и записью появляются точки `await`, где другой запрос успеет вклиниться, и гонки (двойной submit, параллельный webhook) пришлось бы ловить вручную.
- ORM отвергнут: привязывает к диалекту, добавляет зависимость и скрывает именно те запросы, которые нужно проверять тестами.
- Код доказал: интерфейсы с `Promise` на бумаге оказались ненужными, вызывающие слои используют значения напрямую.

## Последствия
- Запись блокирует всю базу: параллельных писателей нет. Для одного магазина это приемлемо, при росте нагрузки станет узким местом.
- Переезд на PostgreSQL потребует переписать репозитории в асинхронные и все вызовы выше них.
- Правило «SQL только в репозиториях» нарушено в каталоге; каждое такое отступление надо держать в голове при смене СУБД.
