# Выход в production: чек-лист

**Этот документ — план. Ничего из перечисленного не выполнялось:** публикация, DNS, платные ресурсы, миграции на боевой БД требуют отдельного согласия владельца. Open Server не годится для production.

## 1. Решения до начала (нужны от владельца)

- [ ] Хостинг и регион. Требование: **постоянный диск** (SQLite-файл и `uploads/` живут на диске). Платформы с эфемерной файловой системой (serverless, контейнеры без тома) не подходят без смены БД.
- [ ] Домен и DNS.
- [ ] Почта: SMTP-сервер, адрес отправителя, получатели уведомлений.
- [ ] Платёжный провайдер и способ доставки (пока заглушки), 1С (`docs/1c.md`).
- [ ] RPO/RTO: как часто копировать и как быстро восстанавливаться (`docs/backup-restore.md`).
- [ ] Юридические тексты, реквизиты, права на фото из фида (`docs/handoff.md`).

## 2. Сервер

- Node.js 24 LTS или новее, npm. Один процесс приложения (SQLite — один писатель; несколько реплик на одном файле не поддерживаются).
- Папка проекта с правом записи в `data/` (или в `DATA_DIR`/`DATABASE_PATH`).
- Процесс-менеджер, который перезапускает приложение после сбоя и при перезагрузке сервера (например, systemd на Linux, NSSM или Планировщик заданий на Windows, pm2). Логи — в файл с ротацией, без секретов.
- Отдельные БД и секреты для staging и production.

## 3. Переменные окружения (`docs/env.md`)

- [ ] `SITE_URL=https://ваш-домен` (без «/» в конце).
- [ ] `SESSION_SECRET` — случайная строка ≥ 32 символов, сгенерировать на сервере, хранить только там.
- [ ] `TRUST_PROXY=true` — только если перед приложением свой обратный прокси.
- [ ] `PAYMENT_WEBHOOK_SECRET` — когда подключается оплата.
- [ ] `MAIL_HOST`, `MAIL_PORT`, `MAIL_USER`, `MAIL_PASSWORD`, `MAIL_FROM`, `MAIL_TO`.
- [ ] `DATABASE_PATH`/`DATA_DIR` — на постоянном диске.
- [ ] **Не** задавать `PAYMENT_PROVIDER=test`: в production тестовая оплата принудительно выключается.
- [ ] `HTTPS_REDIRECT` не задавать (исключение — прокси, не умеющий передавать верный `X-Forwarded-Proto`).

## 4. HTTPS и обратный прокси

Приложение само TLS не терминирует. Перед ним ставится прокси (Nginx, Caddy, балансировщик хостинга) с сертификатом (например, Let's Encrypt) на домен.

- [ ] Прокси передаёт `Host`, `X-Forwarded-For` и **`X-Forwarded-Proto`**. За прокси с TLS-терминацией передавайте `X-Forwarded-Proto: https` — иначе заголовок HSTS не включится (приложение не считает запрос защищённым).
- [ ] Приложение редиректит на HTTPS (301) только когда прокси явно передал `X-Forwarded-Proto: http`; хост редиректа берётся из `SITE_URL`, а не из заголовка `Host`. Адрес `/api/health` редиректом не затрагивается.
- [ ] Прокси ограничивает размер тела запроса (импорт YML — до 20 МБ; остальное меньше) и не раскрывает внутренние порты.
- [ ] Разрешите наружу только 80/443; порт приложения закройте от интернета.
- [ ] После включения: проверить в браузере замок, `Strict-Transport-Security`, отсутствие циклов редиректа.

## 5. Сборка и запуск

```
npm ci
npm run check
npm run build
npm run db:migrate
npm run admin:create -- логин-администратора
npx next start -p <порт>
```

- `npm run start` слушает порт 3000; другой порт — `npx next start -p <порт>`.
- Каталог: `npm run import:yml -- catalog.yml --preview`, затем без `--preview`. Решение по фото: `--images` скачивает копии с `IMAGE_HOST_ALLOWLIST` (права!).
- Миграции применяются и при старте приложения; перед обновлением с миграциями всегда делайте копию.
- Проверка: `/api/health` → 200; `/robots.txt`, `/sitemap.xml`; в админке `/admin/integrations` честно показывает «заглушка» для ещё не подключённого.

## 6. Резервные копии

- [ ] Расписание `npm run backup` (например, ежедневно) планировщиком; копии хранить **вне** диска приложения, срок хранения и ответственный названы.
- [ ] Архив содержит персональные данные покупателей — доступ ограничить, при передаче шифровать.
- [ ] Тест восстановления на staging проведён и записан (`docs/backup-restore.md`).

## 7. Обновление и откат (rollback)

1. `npm run backup`, убедиться, что файл создан.
2. Остановить приложение (процесс-менеджер).
3. Получить новую версию кода, `npm ci`, `npm run check`, `npm run build`.
4. Запустить — миграции применятся (только вперёд, применённые файлы не редактируются).
5. Проверить `/api/health` и ключевые сценарии (заказ, заявка, вход в админку).

**Откат:** остановить приложение → вернуть предыдущую версию кода → `npm run restore -- <копия до обновления> --force` (прежнее состояние сохранится в `data/pre-restore-*`) → запустить. Миграции вперёд-only: откатывать схему можно только восстановлением копии. Заказы, принятые после копии, в неё не попадут — решайте окно обслуживания заранее.

## 8. Мониторинг

- [ ] Внешняя проверка `GET /api/health` (200 + версия миграций; 503 без деталей при проблеме БД).
- [ ] Алерт на заполнение диска.
- [ ] Письма администратору о сбоях обмена с 1С (событие `integration.failed`) работают только при настроенном SMTP.
- [ ] Раздел админки `/admin/mail` — очередь писем и ошибки отправки; `/admin/integrations` — журнал запусков.

## 9. Перед открытием для людей

- [ ] Все метки `[… — впиши]` заменены реальными данными (адрес, часы, email, реквизиты, соцсети, логотип) — `/admin/content/settings`.
- [ ] Юридические страницы утверждены юристом (в БД они помечены черновиком).
- [ ] Сайт не индексируется до готовности (закрыть доступ на staging; robots/sitemap проверены уже на целевом домене).
- [ ] Пароль администратора создан командой `admin:create` на сервере, а не скопирован из разработки; учётные записи разработки не переносятся.
- [ ] Проверен вход менеджера: ему недоступны разделы, закрытые матрицей прав.

## 10. Чего этот план НЕ делает

Не публикует сайт, не покупает домен/хостинг, не меняет DNS, не включает реальные платежи. Каждое из этих действий — отдельное решение владельца.
