# Резервные копии и восстановление

## Что копируется

`npm run backup` создаёт один файл `data/backups/rts-backup-ГГГГММДД-ЧЧММСС.tar.gz` (время UTC). Внутри:

| Файл в архиве | Что это |
|---|---|
| `rts.sqlite` | согласованный снимок БД (SQLite `VACUUM INTO`), приложение при этом **можно не останавливать**; снимок проверяется `PRAGMA integrity_check` |
| `uploads/…` | загруженные и перекодированные фото |
| `onec-outbox/…` | файлы заказов, выгруженные для 1С (по ним БД знает, что заказ уже выгружен) |
| `manifest.json` | версия формата, версия миграций, SHA-256 каждого файла |

**Чего в архиве нет:** `.env`, `SESSION_SECRET`, пароли SMTP, ключи платёжных систем — секреты хранятся отдельно (менеджер паролей, настройки хоста). Нет также `data/backups/` (копии не копируют сами себя) и `onec-inbox/` (входящие файлы можно положить заново).

**Но:** в БД лежат данные покупателей (имена, телефоны, адреса, заказы), хеши паролей и хеши токенов сессий. Архив нужно хранить и передавать так же осторожно, как саму БД: ограниченный доступ, шифрование при выносе с сервера.

Архив — обычный tar.gz: открывается `tar -xf файл.tar.gz` (есть в Windows 10/11) или 7-Zip.

## Создать копию

```
npm run backup
npm run backup -- --out D:\резерв
```

Команда пишет путь, размер, число файлов и версию миграций. Копию кладите **вне диска приложения** (другой диск, облако по решению владельца). Расписание — планировщик ОС (Планировщик заданий Windows / cron) с командой `npm run backup` в папке проекта; удаление старых копий пока вручную или своим скриптом.

## Восстановить

1. **Остановите приложение** (иначе Windows не даст заменить открытый файл БД; на Linux приложение продолжит работать с удалённым файлом).
2. `npm run restore -- путь\к\rts-backup-….tar.gz`
3. Если в папке данных уже есть БД или файлы — команда откажется. Повторите с `--force`: прежние `rts.sqlite*`, `uploads/` и `onec-outbox/` **не удаляются**, а переносятся в `data/pre-restore-ГГГГММДД-ЧЧММСС/`.
4. Запустите приложение. Если копия старее текущего кода, недостающие миграции применятся при старте.

Что проверяет `restore` до замены данных: архив читается без ошибок; в нём только разрешённые пути (`rts.sqlite`, `uploads/`, `onec-outbox/`, `manifest.json`; пути с `..`, абсолютные и ссылки отклоняются); состав совпадает с манифестом; SHA-256 каждого файла совпадает; БД проходит `integrity_check`. Если замена не удалась на середине, прежние файлы возвращаются на место.

## Проверка восстановления

Тест `tests/backup/backup-restore.test.ts` проверяет цикл «копия → потеря данных → восстановление»: товар и цена в БД, содержимое файлов `uploads/` и `onec-outbox/`, удаление лишнего, отказ без `--force`, отказ при повреждённом архиве и при пути `../`. Руками на копии: `npm run backup`, затем `restore` в пустую папку с другими `DATABASE_PATH`/`DATA_DIR` и открыть `/api/health`.

**Периодически (раз в квартал и перед крупным обновлением) проводите тест восстановления на staging** — копия без проверенного восстановления не считается резервом.

## Что здесь не решено

- RPO/RTO и расписание — решение владельца (`docs/handoff.md`).
- Шифрование архивов, выгрузка в облако, автоудаление старых копий — не реализованы.
- Копия БД согласована сама по себе, но `uploads/` копируется отдельно во времени: фото, загруженное в момент копирования, может не попасть в архив — тогда оно «осиротеет» ссылкой в БД, пока импорт со `--images` не скачает его снова.
